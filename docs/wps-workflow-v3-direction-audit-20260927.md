## 必须纠正的实现与记录问题

### 1. 已复现：拆分待核对可自行变成功（R10）

路径：`split-store.prepare()` → `split-state.reconcile()`。已有pending回执但目标存在时，第一次把实际SHA写进 `file.sha256` 并置待核对；第二次只比较同一SHA，便提升为成功。没有与应输出的 `modelSnapshot` 比较任何单元格。

本机最小复现得到 `pending → needs-verification → succeeded`，`contentVerified=false`。这违反handoff 4.4“比对实际内容后才能认成功”。应将观察SHA与已验证内容证明分开；仅重复刷新、重启、SHA稳定不能解除待核对。

### 2. 已复现：候选暂存清理的两个缺陷（未提交改动）

`dev/export-files.cjs` 的 `discard()`先删票据，再判断已经发布；返回 `already-published` 后原来有效的 `verify()`反而报会话失效。另一个候选清理按10分钟mtime删除文件，而票据有效期为1小时；实测11分钟前mtime且票据仍有效的stage被第二次prepare删除。应保护有效/正在使用的票据；已发布的清理不得损坏发布/核验状态。上述诊断只用隔离scratch文件，无真实成果被改动。

### 3. 已确认：公开审计仍有旧规则（R12/R13）

`dev/audit-outputs.py` 把匹配电话/邮箱或长数字的任何单元格列入 `personal`，并直接使 `ok=false`；这会拒绝明确允许的询价抬头联系方式，甚至误伤长编码。`dev/release-audit.cjs` 的expected cells为可选局部清单，不能独立证明没有额外未预期公开值。

应基于冻结的预期完整单元格矩阵逐值核对，并允许预期抬头位置上的指定联系方式；意外联系方式/路径/内部列仍不允许。内部总簿和供应商拆分件分开审计：总簿允许明确内部页，拆分件不得有内部/隐藏页或隐藏追溯列。原0.2清单一概写“无内部页”比4.4更严且矛盾，本次交接已纠正。

### 4. 已确认：完成状态与部分界面缺口

- 历史R2/R7等被勾为完成，却挂着真实WPS出口；R6又仍写“未做真机”，与最新4文件证据冲突。改用“代码已有/部分真机/待补齐/已验收”分别记录。
- Ribbon仅2按钮，缺阶段快捷入口；补导航即可，不能由快捷按钮偷偷执行确认、学习、生成或拆分。
- 汇总标题/跨行表头布局与图有局部差距。修正现有layout即可，不改变字段和工作流。
